# DektopOS — working notes

Last updated: 2026-09-25. Read this before touching anything; a lot of
time was lost to bugs that this file now explains.

DektopOS is a 32-bit x86 hobby OS written in NASM, booted from a floppy
image. It runs in 320x200x256 VGA mode 13h, draws a synthwave wallpaper,
and runs a small window manager with six applications.

---

## 1. Build and run

```sh
./build.sh            # -> out/dodos.img       (1.44 MB floppy)
./build.sh hd         # -> out/dodos-hd.img    (16 MB USB/HDD)

qemu-system-i386 -drive file=out/dodos.img,format=raw,if=floppy -m 32
```

`build.sh` assembles `src/boot.asm` (512 B MBR) and `src/kernel.asm`,
concatenates them and pads the kernel to a sector boundary. The current
kernel is **18653 bytes = 37 sectors**; the image is 1474560 bytes.

### The one build constraint you must not break

`src/boot.asm` reads a *fixed* number of sectors, so the kernel can only
be as large as that constant:

| symbol            | value    | meaning                          |
|-------------------|----------|----------------------------------|
| `KERNEL_LBA`      | 1        | first sector after the MBR       |
| `KERNEL_ADDR`     | `0x10000`| linear load address              |
| `KERNEL_SECTORS`  | 128      | 64 KB ceiling, ends at `BACKBUF` |
| `BACKBUF`         | `0x20000`| 320x200 frame buffer             |

`build.sh` now reads `KERNEL_SECTORS` out of `src/boot.asm` and **fails
the build** if `kernel.bin` is larger than that. Keep the ceiling above
the kernel size; the maximum is 128 sectors.

This was the single biggest time sink. It used to be 32 sectors while the
kernel had grown to 37, so everything past offset `0x4000` was silently
never loaded and the CPU ran into zeroed memory. The symptom was
baffling: the boot splash drew fine, then execution appeared to "hang"
with no fault. What gave it away was a GDB step trace that advanced EIP by
two bytes per step with ESP unchanged — the signature of executing
`00 00` (`add al,[eax]`) in a region of zeros.

## 2. Memory map at runtime

| range            | contents                                  |
|------------------|-------------------------------------------|
| `0x0000-0x7C00`  | BIOS data, IVT                            |
| `0x7C00`         | boot sector (loaded by BIOS)              |
| `0x10000-...`    | kernel, loaded at `KERNEL_ADDR`           |
| `0x20000-0x23200`| `BACKBUF`, 320x200 indexed frame buffer   |

**Address arithmetic** (this tripped up several debugging rounds):

```
runtime address = 0x10000 + offset within kernel.bin
file offset in the image = 0x200 + offset within kernel.bin
```

So `shell_init` at kernel offset `0x47CD` is runtime `0x147CD` and lives
at file offset `0x49CD` in the image — not `0x47CD`.

To map a label to an address, regenerate the listing and use the helper:

```sh
nasm -f bin -I src -l /tmp/k.lst -o /tmp/t.bin src/kernel.asm
python3 tools/sym.py /tmp/k.lst wm_count shell_init
```

Re-derive these after any rebuild; they move with code size:

```sh
nasm -f bin -I src -l /tmp/k.lst -o /tmp/t.bin src/kernel.asm
python3 tools/sym.py /tmp/k.lst wm_count wm_focus shell_init
```

`tools/sym.py` handles both plain code labels (address is the next
instruction) and data labels such as `wm_windows: times ... db 0` (address
is on the label's own line).

## 4. Test harness

`tools/drive.py` is the right tool — it is a full QMP harness, not just a
screenshotter:

```sh
python3 tools/drive.py out/dodos.img script.txt shots/
```

Script commands, one per line:

```
wait <ms>                  sleep
key <qcode>                press + release
hold <qcode> / release <qcode>
type "text"                type ASCII
move <x> <y>               absolute mouse move
click <left|right|middle>
dblclick <left|right>
drag <x1> <y1> <x2> <y2>
shot <name>                screenshot -> shots/<name>.ppm + ASCII art
log <name>                 dump the serial log
```

It writes `shots/serial.log`, so the serial console is the fastest way to
see how far boot got. Output order on COM1:

```
1L6600P[k] 00010000   BIOS + MBR
1234567               kmain init steps
...i (x118)           boot progress bar
abcdef 9 [ok]         shell_init markers, then main loop entered
Cc Cc Cc ...          gfx_textc enter/exit, six per frame
```

`Cc` pairs are `gfx_textc` entry/exit markers in `gfx.asm`. Six per
frame means one frame completed; fewer than that in the log means the
loop died partway through drawing.

Other helpers, all in `tools/`:

| tool            | purpose                                              |
|-----------------|------------------------------------------------------|
| `sym.py`        | label -> runtime address from a NASM listing         |
| `gdbmon.sh`     | boot headless with a GDB stub on `tcp::6677`         |
| `stopq.sh`      | kill any running QEMU (use this before every attach) |
| `shot.sh`       | screenshot + serial capture, `shot.sh <tag> <secs>`  |
| `mkfont.py`     | regenerate `font8x8.inc`                             |
| `mkkbd.py`      | regenerate `kbdmap.inc`                              |
| `fontdump.py`   | dump font glyphs                                     |

The three shell helpers keep their sockets and images under
`/tmp/opencode` and create it if missing, because **`/tmp` does not
survive a reboot** (this cost a full rebuild of the tooling once already).

A GDB session looks like:

```sh
./tools/stopq.sh
setsid ./tools/gdbmon.sh >/dev/null 2>&1 &
sleep 4
gdb -q -batch -ex 'set confirm off' -ex 'target remote :6677' \
    -ex 'break *0x148a6' -ex continue \
    -ex 'printf "count=%d focus=%d\n", *(int*)0x13420, *(int*)0x13424' \
    -ex kill
```

## 5. Debugging traps

1. **`pkill -f qemu-system-i386` kills your own shell** — the pattern
   matches the command line running it. Use `pkill -9 -x qemu-system-i386`,
   then confirm with `ps -e -o pid,comm= | grep qemu`.

2. **A stale QEMU holding GDB port 6677 will silently attach you to a
   different machine.** A leftover instance from an earlier build made
   several rounds of debugging meaningless — the memory looked plausible
   but belonged to old code. Kill QEMU *before* every `target remote`.

3. **`/tmp` does not survive a reboot.** `drive.py` recreates its QMP
   socket under `/tmp/opencode`, so that directory must exist.

4. **`serial_putc` output can be buffered** — the file may not grow
   immediately. Check size across two samples, not once.

5. When a routine "hangs", single-step with GDB and watch **ESP as well as
   EIP**. An unchanging ESP with EIP creeping forward by 2 means you are
   executing zeros, not looping.

### Recently fixed — do not "re-find" these

**1. Kernel tail was never loaded** (the big one, see section 1).
`KERNEL_SECTORS` was 32 while the kernel needed 37.

**2. `gfx_sprite` leaked 8 bytes of stack per row.** The vertical-zoom loop
did `push ecx; push ecx` at `.vrow` but only one `pop ecx` before jumping
back, so the epilogue's `pop ebp; ret` returned to a garbage address.
Rewritten with clean locals and screen clipping:

```
[ebp-4] rows left, [ebp-8] columns that fit, [ebp-12] source stride
```

The clipping also stops sprites at the right/bottom edge from wrapping into
the next scanline. `gfx_bevel` was checked and is balanced — its
`add esp, 16`/`add esp, 20` values are argument counts, not leaks. Don't
"fix" it again.

## 6. Current state

**The main loop now runs indefinitely.** Screenshot at t=9s shows the
wallpaper, taskbar and window chrome; serial output repeats the frame cycle
forever. `shell_init` completes (`abcdef9[ok]`).

### The real root cause of the one-frame crash — FIXED

`wm_desk_icons` in `src/wm.asm` cleaned up **6** dwords after a call that
pushed only **5** arguments:

```asm
    push dword C_WHITE              ; arg5 bg
    push dword C_NAVY               ; arg4 fg
    push eax                        ; arg3 str
    push dword ebx                  ; arg2 y
    add dword [esp], 13             ; y = y + 13
    push edx                        ; arg1 cx
    call gfx_textc                  ; reads [ebp+8] .. [ebp+24] = 5 args
    add esp, 24                     ; BUG: removed 6, not 5
```

`gfx_textc` is correctly balanced, so it returned to the caller's expected
`esp`. The extra dword of cleanup then raised ESP by 4 bytes per icon. After
6 icons ESP was 24 bytes too high, so the function's own `ret` popped a
non-return address (`0x00000000`) and jumped to address 0.

**Fix: `add esp, 20`.**

The adjacent `gfx_sprite` call was already right (6 args, `add esp, 24`) —
do not "balance" the two to match each other.

### How it was found (reusable method)

The obvious reads all looked correct, so the leak was measured instead of
guessed. Two things made the measurement trustworthy:

1. **Probe ESP, don't infer it.** Serial markers printed a char at each step;
   walking the marks only showed that `wm_desk_icons` reached `.out`.
2. **Wrap every probe in `pushad` / `popad`.** A probe that calls
   `serial_hex32` (which itself calls `serial_putc`) perturbs the very
   quantity being measured. With bare probes the numbers were wrong; with

```asm
    pushad
    mov al, 'S'
    call serial_putc
    mov eax, esp
    add eax, 32            ; undo pushad's own 32 bytes
    call serial_hex32
    popad
```

the drift was exact and constant: `+4` per icon, `0` across `gfx_sprite`.

GDB agreed and localised it in one shot: break on `wm_desk_icons`'s `ret`,
and a hardware watchpoint on the return-address slot showed the slot being
clobbered by a nested `call`. Do **not** trust `pushad`-less probes — that is
the one trap in this method.

### Also fixed earlier

- `wm_focus_set` read `[esp+8]` (the return address) instead of `[esp+12]`,
  writing a code address into `wm_focus`. Real bug, but **not** the crash
  cause. See section 5.
- `wm_desk_icons` was missing the `push eax` title pointer entirely, so
  `gfx_textc`'s `str` argument was garbage.

### Open bug — `wm_drag_move` y-clamp is wrong

`src/wm.asm`, `wm_drag_move`:

```asm
    mov edx, [eax + WINDOW.y]
    add edx, [eax + WINDOW.h]
    sub edx, SCRH - TASKBAR_H - 2
    cmp ecx, edx              ; max y computed as y + h - 180
```

Should be the work-area height minus the window height:

```asm
    mov edx, SCRH - TASKBAR_H - 2
    sub edx, [eax + WINDOW.h]
```

Still unexercised — dragging has not been tested now that the loop survives.

## 7. Desktop overhaul — in progress (session 2)

### Fixed this session

**Three bugs in `gfx_sprite`**, all in the rewrite from session 1. The blitter
was writing to `BACKBUF * y + x` instead of `BACKBUF + y*SCRW + x`, so every
sprite (6 app icons *and* the cursor) was scribbled 3–13 MB into RAM, outside
the framebuffer, trampling window and app data. That is why there was no
cursor, no icons, and garbage colour bands in the windows.

1. `imul edi, [ebp + 12]` multiplied instead of offsetting. Now computes
   `y * SCRW` and adds it to `BACKBUF`.
2. The row loop never advanced to the next scanline, so every source row drew
   on top of the previous one. Destination row base is kept in `[ebp-16]`
   (locals grew to `sub esp, 20`) and bumped by `SCRW` per source row.
3. The row clamp was inverted and always kept the larger of
   available/requested rows.

Verified: desktop frames are now pixel-identical 2 s apart, and the frame
changes when the mouse moves.

**Palette widened to 256 entries.** `gfx_init` now calls `build_ramps`
(`src/gfx.asm`), which interpolates 10 ramps from a descriptor table
(`ramp_defs`, 8 bytes each: base, count, r0,g0,b0, r1,g1,b1). Entry `i` is
`start + ((end - start) * i) >> 4`. Entries 0–15 are untouched, so every
existing `C_*` constant still works. Ramp bases: 16 blue, 32 teal, 48 green,
64 gold, 80 orange, 96 red, 112 pink, 128 purple, 144 light neutral,
160 dark neutral. **Nothing uses the new indices yet** — they are staged for
the panel and title-bar gradients.

### Gotcha: boot takes ~10 s, not 5

`drive.py` scripts must `wait 15000` before `shot`. At `wait 9000` the shot
still catches the boot splash (diagonal sweep + progress wedge), which looks
superficially like a corrupted desktop. Two shots of the same build taken 2 s
apart differed by 54% of pixels purely because one caught the splash and one
caught the desktop. Always confirm a frame is stable before diagnosing it.
